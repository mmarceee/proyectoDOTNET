# Identity en CU-40, CU-41 y CU-43

Fecha: 14/10/2026. Se integró main (Identity, PR #20) en la rama de trabajo, conservando Blazor 10.0.13 y EF Core/Relational 10.0.12.

`TenantDeSesion` resuelve el operador y comercio desde la cookie autenticada; nunca usa el operador provisorio para un usuario con sesión. `ResponsablePlanificacion` lee NameIdentifier y los handlers existentes registran ese responsable en validaciones, retiros, transiciones y RutaDespachada. No se consultan las tablas de Identity desde los handlers de Planificación.

Se ajustó `AccesoPlanificacion`: una sesión autenticada siempre requiere rol Despachador y un operador válido sin contexto de comercio. El respaldo sin sesión sólo existe en Development, con Identity:PermitirTenantProvisorio y Planificacion:HabilitarDesarrolloSinIdentity habilitados. Administrador no hereda el permiso de Despachador. La opción de desarrollo no permite eludir el rol de un usuario autenticado.

Sin respaldo, la API devuelve 401; las páginas de Planificación redirigen al login con ReturnUrl. Un usuario autenticado sin permiso recibe 403. Las escrituras con cookie siguen requiriendo antiforgery. Los avisos de modo de desarrollo sólo aparecen cuando se trabaja sin sesión.

Por decisión posterior de Lucas, la configuración de la aplicación exige login también en Development: Identity:PermitirTenantProvisorio y la opción de Planificación de ambos perfiles de Visual Studio quedan en false. AccesoAplicacionesMiddleware en el host protege /backoffice y /portal (incluido index.html y recursos) después de leer la cookie. El login, sus recursos compartidos y el seguimiento público permanecen accesibles. Los permisos por perfil y operador siguen en los casos de uso. El respaldo se habilita explícitamente sólo en los fixtures históricos que preparan datos sin sesión; las pruebas de las entradas privadas lo desactivan.

Las pruebas de `PlanificacionIdentityTests` usan la página real de login, cookies y HTTPS, sin reemplazar la autenticación por un esquema simulado. Cubren CU-40/CU-41/CU-43, responsable y operador del Outbox, separación de rutas entre Demo y Este, rechazo de administradores/comercio incluso con las opciones de desarrollo activas, redirección de Backoffice y antiforgery. El token se obtiene nuevamente después del login porque pasa a estar vinculado a la identidad autenticada.

Los envíos de prueba se preparan mediante el respaldo de desarrollo; las operaciones de Planificación se ejecutan con sesión real. Esto no implica que los restantes módulos hayan completado su propia integración de permisos.

Verificación: 54 pruebas de arquitectura y 46 unitarias aprobadas tras integrar main. La ejecución completa de integración tuvo 124 aprobadas y una expectativa antigua de 401 en Backoffice fallida por la nueva redirección al login; se actualizó esa prueba para comprobar 302 y la URL de ingreso. La ejecución final de Planificación, con los últimos ajustes, aprobó sus 52 pruebas (incluidas siete con Identity real), sin fallos ni omitidas. Se usó `--artifacts-path artifacts/identity-verificacion` para no interferir con la API en ejecución.

Para ejecutar esta versión desde Visual Studio, reiniciar la API y usar el perfil https de Logistica.slnx. En Docker, reconstruir la API según el flujo de Compose del proyecto. Las migraciones y el seed de Identity se ejecutan junto al arranque cuando Database:MigrateOnStartup está habilitado. No es necesario borrar la base de datos.

Verificación final con login obligatorio en las entradas: **129 pruebas de integración, 54 de arquitectura y 46 unitarias aprobadas**, sin fallos ni omitidas. Se comprobaron las redirecciones de /backoffice, /backoffice/rutas, /portal y /portal/index.html en Development, el acceso posterior con cookie real y la continuidad del seguimiento público. Los fixtures de layout/assets habilitan explícitamente el respaldo para comprobar esos recursos; el entorno normal permanece protegido.

El menú del Backoffice muestra el correo autenticado y Cerrar sesión. El botón usa POST /cuenta/salir con antiforgery y el servicio de sesión existente. La comprobación de logout verifica rechazo sin token, continuidad de sesión ante ese rechazo, cierre válido y posterior redirección al login desde Backoffice y Portal. Las 13 pruebas de Identity y layout seleccionadas pasaron. Crear un usuario no crea un conjunto vacío de datos: el personal comparte los datos de su operador; la cuenta de despacho Demo pertenece al mismo operador utilizado por las pruebas previas.

El listado de rutas permite combinar fecha y estado (Todos, Planificada, Despachada, EnCurso y Finalizada). La consulta filtra en PostgreSQL antes del límite de 100 resultados y mantiene el filtro Tenant. Los estados desconocidos se rechazan. Por decisión de Lucas, el login exitoso siempre redirige al inicio de su aplicación: /backoffice para personal y /portal/ para comercio. Se ignora cualquier ReturnUrl, de listado, detalle o sitio externo. La verificación previa de Planificación aprobó 62 pruebas; las pruebas de retorno se adaptaron a esta regla.

Se separaron las entradas: /cuenta/ingresar es del personal y /portal/ingresar es del comercio. Comparten IServicioSesion e Identity, con un tipo de acceso que comprueba perfiles antes de emitir la cookie. Un comercio no puede autenticarse por el login del personal, ni viceversa. El Portal requiere UsuarioComercio y un comercio identificado en la cookie; Backoffice y /api/deposito rechazan las cuentas de comercio, incluso si ya tienen una cookie válida. El middleware decide en el servidor; ocultar enlaces no constituye el control de acceso. El ingreso del Portal tiene un layout sin las opciones de personal. La selección del operador del comercio (CU-03) sigue siendo una dependencia separada: no se inventa un operador para la sesión del comercio.

El menú del Portal permite salir mediante /cuenta/salir?portal=true. GET muestra una confirmación sin cerrar la sesión; POST protegido por antiforgery cierra la cookie y vuelve a /portal/ingresar. El cierre desde el Backoffice vuelve a /cuenta/ingresar.

La aplicación del repartidor usa /repartidor/ingresar, exige Perfil.Repartidor y un operador válido en la cookie, y abre siempre /repartidor/ después de iniciar sesión. Repartidores, comercio y personal tienen entradas separadas y no pueden usar las otras aplicaciones con su cookie. El logout de la PWA usa /cuenta/salir?repartidor=true y vuelve a su propio login. El seed agrega repartidor@operador-demo.uy y repartidor@envios-del-este.uy, con la contraseña de demostración existente. Requiere reiniciar la API con Database:MigrateOnStartup para ejecutar el seed idempotente. Esto acredita rol y operador; vincular Usuario al recurso Repartidor y descargar su hoja de ruta queda para la ejecución de CU-50.

El service worker publicado consulta la red primero para navegación, de modo que no sustituya una redirección al login por un index cacheado. Ante fallo de red conserva el shell previamente descargado; el login no se sustituye por ese shell y requiere conexión. La gestión de identidad local y datos cifrados offline queda dentro del trabajo de CU-50. La suite .NET pasó 246 pruebas (146 integración, 54 arquitectura y 46 unitarias); tres pruebas Node del service worker verificaron redirección, fallback offline y login sin conexión. Comando: node --test scripts/tests/repartidor-service-worker.test.cjs.
